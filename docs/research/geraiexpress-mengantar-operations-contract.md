## 2. (a) Pickup and time reservation

Anchors: `#content-add-time`, `#content-get-time`, `#content-add-order`, `#content-add-address`, `#content-get-addresses` (Public). Access date 2026-10-28.

### 2.1 `POST {BASE_URL}/api/public/{API_KEY}/time` — "Add Time"

Request body (Observed, `#content-add-time`):

| Field | Type | Documented content |
|---|---|---|
| `address_id` | String | "user's address _id" (the pickup address record from the address endpoints) |
| `date` | String | "mm-dd-yyyy format" (example `11-27-2022`) |
| `time` | String | one of `9:00, 10:00, 11:00, 12:00, 13:00, 14:00, 15:00, 16:00, 17:00, 18:00` |

Response (Observed, example only): `success`, `data` with `isSunday` (boolean), `status` (example `"empty"`), `_id` (the time id), `date` (ISO timestamp, example `2026-02-03T00:00:00.000Z`), `time` (`"13:00"`), and an `address` object (`_id`, `PICKUP_NAME`, `PICKUP_ADDRESS`, `PICKUP_CITY`, `PICKUP_REGION`). The documentation describes the route only as "Pickup time used in order creation". The `_id` is what `pickup.time_id` of Create Order expects (Observed, `pickup.time_id` row: "time _id (required for type 'scheduledPickup')").

Constraint (Observed): "The pickup schedule (`date` + `time`) must be at least **90 minutes** from the current time. A request with a pickup time less than 90 minutes ahead will return an `invalid pickup time` error." The page does not give the HTTP status for that error, the error body shape, or the clock/time zone the 90 minutes is measured in.

Contradiction (Observed 2026-11-02, lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): the web UI's earliest selectable pickup is "2 jam dari waktu saat kamu membuka halaman buat pesanan" (help 14715371). Until Mengantar clarifies, GeraiExpress uses the stricter 2 hours as a configurable lead time (T-043 amendment).

### 2.2 `GET {BASE_URL}/api/public/{API_KEY}/time` — "Get Time"

Response (Observed, example only): `data` is an array of `{_id, date, time}`. In the example `date` is epoch milliseconds (`1677240000000`, `1703239200000`) with `time` `"12:00"` / `"10:00"`. Arithmetic on the examples (Evidence, computed here): those epoch values are `2023-02-24T12:00:00Z` and `2023-12-22T10:00:00Z`, i.e. the UTC clock reading equals the `time` string. Whether the stored instant is Jakarta local time written as UTC is **Unknown**; the POST example instead returns a midnight `00:00:00.000Z` date for a `13:00` slot, so the two examples do not share one representation. The page has no query parameters, no description, and does not say what the list contains.

[Assumption] The list holds the seller's own previously created time records, because the example ids are shaped like the POST response id and the route has no inputs. Earlier observation (Observed, T-020, 2026-10-14): sandbox `GET /time` returned `data: []` for a seller that had created none, which does not contradict the assumption but does not prove it.

### 2.3 The `pickup` object of Create Order

Observed (`#content-add-order`, body parameters and curl examples):

| Field | Type | Documented content |
|---|---|---|
| `pickup` | Object | "Pickup data" |
| `pickup.address_id` | String | user's address `_id` |
| `pickup.type` | String | `scheduledPickup` or `dropOff` |
| `pickup.time_id` | String | time `_id`; required for `scheduledPickup` |
| `pickup.volume` | String | `volumeTruck`, `volumeMobil`, `volumeMotor`; required for `scheduledPickup` |

Documented per-courier constraints:

| Courier | Rule (Observed) |
|---|---|
| `spx` | `dropOff` is accepted only when SPX Drop Off is enabled for the account, otherwise the request is rejected ("use `scheduledPickup` or contact admin"). For `scheduledPickup`, the date/time that `time_id` resolves to is checked against SPX's own live pickup slots for that day before the order is created; a date/time outside every open slot "is rejected with the slots that are actually available that day". Slots change per day. |
| `pos` | For a scheduled pickup "the selected pickup address must contain valid `pinpointData.lat` and `pinpointData.lng`"; pinpoint is set through Add address (`pinpointData`, latitude −90..90, longitude −180..180) or sent as `null`/omitted when unavailable. |
| Others | The API page states only the generic rules above: no per-courier slot lists, no maximum days ahead, no per-slot capacity, and no restriction on Sundays beyond the unexplained `isSunday` flag. Update 2026-11-02 (lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): per-courier pickup cut-off times come from help 5502313 (updated 2026-09-24), not the API page: JNE 15:00, SiCepat 12:00, SAP 15:00, iDexpress 11:00, J&T 12:00, Lion 15:00, Anteraja 15:00 (pickup only), Pos 16:00, SPX 15:00; pickup SLA 7 days for most couriers, SAP up to 3 failed pickups, iDexpress and SPX 14 days. Whether a cut-off bounds the same-day slot or the order-creation time, and whether the API enforces it, is Unknown. Pickup minimum volume: Unknown. |

Order item response fields touching pickup (Observed, example): `PICKUP_DATE` (`"2026-06-01"`), `PICKUP_TIME` (`"12:00:00"`), `PICKUP_NAME`, `PICKUP_ADDRESS`, `PICKUP_CITY`, `PICKUP_REGION`, `PICKUP_DISTRICT`, `PICKUP_PIC_PHONE`.

### 2.4 Pickup error and status taxonomy

| Case | Documented | Label |
|---|---|---|
| Pickup less than 90 minutes ahead | `invalid pickup time` error; no HTTP status stated | Observed (text) / Unknown (status, body) |
| SPX slot not open | Rejection naming available slots; body shape not shown | Observed / Unknown (shape) |
| SPX dropOff without feature | Rejected; message not shown | Observed / Unknown (shape) |
| Pos without pinpoint | Not shown as an error string | Unknown |
| Anteraja drop-off | Not in the documentation. Observed earlier in the sandbox: 400 `Ekspedisi Anteraja tidak mendukung pengiriman Drop Off` | Observed (T-020 note), not documentation |
| Statuses after a pickup attempt | `PENDING PICKUP`, `PICKED UP`, `PICKUP FAILED`, and `PICKUP_FAILED_API` (the last appears only in the delete rule) | Observed (§5, §3) |

### 2.5 Consequences

- [Proposal] A pickup order needs three provider calls in sequence: ensure the address record exists (with `pinpointData` for `pos`), reserve a time (`POST /time`), then create the order with `pickup.type=scheduledPickup`, `pickup.volume`, `pickup.time_id`. The documentation gives no idempotency key for any of the three; reuse of a `time_id`, its expiry, and whether `POST /time` with the same inputs returns the same record or a new one are **Unknown**.
- Current code supports drop-off only (`src/lib/mengantar/public-api.ts:524` sends `{ address_id, type: "dropOff" }`; comment `:465` says scheduled pickup needs time slots). Pickup is a launch requirement (owner decision); this section is the documented starting point for its design.

## 3. (b) Order cancel and batch deletion

Anchors: `#content-delete-order`, `#content-delete-batch`. Access date 2026-10-28.

### 3.1 `DELETE {BASE_URL}/api/public/{API_KEY}/order`

Request (Observed): JSON body with a `Content-Type: application/json` header.

| Field | Type | Documented content |
|---|---|---|
| `courier` | String | one of `JNE`, `SiCepat`, `Sap`, `iDexpress`, `JT`, `Ninja`, `lion`, `anteraja`, `pos`, `spx`; `Ninja` stays valid for orders created before 2026-09-01 |
| `ids` | Array | "Array of ids" (the example holds 24-hex strings; the response echoes them as `deletedOrderIds`) |
| `orderIds` | Array | optional array of `ORDER_ID`; the page says "if ids is exists, then do not send orderIds, or else, it will override the ids" — the wording is ambiguous about which wins |

Response (Observed, example only): `{success: true, message: "2 orders are deleted from 2 selected orders", deletedCount: 2, deletedOrderIds: [...], deletedOrderIdsHumanReadable: [...]}`.

Eligibility (Observed): an order can be deleted only while its status is `active`, `error`, `PENDING PICKUP`, `PICKUP FAILED`, or `PICKUP_FAILED_API` (or has no status yet). "This rule is the same for every courier". Past pickup (picked up, in transit, delivered, RTS) "the request simply skips that order". The skip is silent in the sense that the documentation shows only `deletedCount` against the selected count; the request-level result for a skipped order (HTTP status, per-order reason) is **Unknown**.

Courier timing (Observed): Anteraja orders "can only be deleted **after 5 minutes** from order created"; earlier deletion "returns an error asking you to wait". For every other courier "there is no fixed waiting time on Mengantar's side once the order already has a tracking number"; the request is forwarded to the courier's API and "succeeds or fails based on that courier's own status/timing rules". If the courier refuses, the order is not deleted and the courier's error message is returned. The page therefore makes cancellation a courier-owned, possibly asynchronous-looking outcome without saying whether the call blocks until the courier answers or what HTTP code a refusal has.

Not documented (Unknown): money effect (refund of the shipping fee or COD fee to the seller balance), whether a deleted order's tracking number is invalidated at the courier, behavior for an unpaid order (`isPaid: false`, no `cnote_no`), the error body shape, partial success (some ids deleted, some refused) semantics beyond the count, idempotency of a repeated delete, and whether a deleted order appears afterwards in `GET /order` (the list example carries `isDeleted`, and Get orders has no filter for it; the label request refers to "non-deleted" orders). Lane D (2026-11-02) found no change for `DELETE /order`: its refund remains Unknown.

### 3.2 `DELETE {BASE_URL}/api/public/{API_KEY}/batch`

Request (Observed): `{courier, id}` where `id` is "Batch id" (the curl example reuses the same `6332f9dfdeff6b0cae5e6c11` string used for an order id in the delete-orders example). Response (Observed): `{success: true, deletedCount: 1}`.

Update 2026-11-02 (CHANGED, lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): the documented response is now `{success, deletedCount, unDeletedCount, totalCount, message}`; deleting a draft batch returns 0 counts plus `isBatchDraft: true`; for couriers `lion`, `anteraja`, `pos` and `spx` only, the response also carries `ordersCount`, `totalBalanceRefund` ("the balance returned") and `errorMessages` (orders the courier refused to cancel).

Unknown: whether `id` is the batch `_id` or the batch code, which orders a batch delete covers, whether paid or picked-up members block it, whether the eligibility and courier forwarding rules of §3.1 apply to each member, refund behavior and refused-order reporting for `JNE`, `SiCepat`, `Sap`, `iDexpress` and `JT` (not documented), and error shapes.

### 3.3 Consequences

- [Proposal] A cancel command in GeraiExpress must be treated as an operation with an unknown outcome until the order is read back, never as a boolean: after any cancel request, reconcile by reading the order (`GET /order?order_id=`) and trust `status`/`isDeleted` rather than the delete envelope alone. This follows the project rule that unknown results reconcile their original operation.
- The current transport cannot send `DELETE` (`src/lib/mengantar/public-api.ts:116` chooses only `GET` or `POST`).

### 4.1 Provisioning

| Fact | Label | Source |
|---|---|---|

Until set, there is nothing to sign and `callbackSecret` is `null`. | Observed | Partner `#content-use-api-key` |
| The channel for the "verification code" is not stated. | Unknown | `#content-webhook` |
| Whether the URL may carry a query string or must be a bare origin and path is not stated. | Unknown | `#content-webhook` |

### 4.2 Delivery contract

Observed (`#content-webhook`, "What we send"):

```
POST <the seller's Webhook URL>
Content-Type: application/json
x-timestamp: <milliseconds since epoch>
x-signature: <hex>
x-environment: sandbox            (sandbox deliveries only; not part of the signature)

{"cnote_no": "...", "order_id": "...", "courier": "...", "status_category": "..."}
```

- `cnote_no` is the AWB, `order_id` the Mengantar order number (`ORDER_ID`), `courier` the courier, `status_category` "the only status we send". The raw courier status is deliberately not included.
- **The payload carries no seller or account identifier.** (Observed: the four fields above are the complete documented body.)
- The values of `status_category` are listed in §5; the page tells receivers to keep a default branch because the list is open-ended.

### 4.3 Signature scheme

Observed (`#content-webhook`, "Verifying the request"): HMAC-SHA256, hex, of the string `{x-timestamp}.{raw request body}` (a single dot), keyed with the seller's Webhook Secret; compare with `x-signature` in constant time; use the raw bytes as received, not a re-serialized body. Verification is called "optional" by the provider but "strongly recommended"; the provider states it does not send from a fixed set of IP addresses, so an IP allowlist "is not an option" and "the shared secret is the only thing that separates a genuine update from a forged one". The page supplies a test vector with a published example secret; use it as a unit-test fixture rather than copying values here.

`x-timestamp` is in **milliseconds**, unlike the Partner API `timestamp` header (seconds) — Observed difference between the two pages. The page's example code rejects anything older than five minutes (a suggestion: "optional: reject anything older than a few minutes").

Note: the Partner request signature is a plain SHA-256 over a colon-joined string; the webhook signature is an HMAC. The two schemes, headers and timestamp units differ (Observed).

### 4.4 Retry, ordering, pause

| Rule | Label | Source |
|---|---|---|
| Any `2xx` acknowledges; the provider waits at most 5 seconds; redirects are not followed. | Observed | `#content-webhook` "Responding and retries" |
| A failed delivery is retried up to 3 times, roughly 1 s, 5 s and 15 s later; delivery is best effort; if all attempts fail the update is not resent. Reconcile with `GET …/order`. | Observed | same |
| Deliveries can arrive out of order after a retry, and the same status can arrive more than once; use `x-timestamp` rather than arrival order. | Observed | same |
| If an endpoint fails 20 updates in a row within 24 hours, delivery to it is paused automatically; a successful delivery resets the count; resume by pressing "Aktifkan kembali" in the seller's settings or re-saving the URL (no verification code needed). Updates that changed while paused are not resent. | Observed | `#content-webhook` "If delivery is paused" |
| Whether a `401`/`403` response (a deliberate signature refusal) also counts toward the 20-failure pause is not stated. | Unknown | — |

### 4.5 Secret handling and the per-seller relationship

Observed:

- The Webhook Secret belongs to a seller's Webhook configuration. It can be regenerated on its own in the seller's settings, and "regenerating the **API key** also replaces the Webhook Secret — your Webhook URL is kept, but you will need to update the secret in your system" (Public). Partner `sellers/api-key/regenerate` has the same effect and returns `data.callbackSecret` (a new secret when the seller has a Webhook URL, else `null`) (Partner `#content-regenerate-api-key`).
- Update 2026-11-02 (NEW, help 14715369 updated 2026-10-17, lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): a seller can generate or regenerate their own Public API key in the Mengantar web app after an email OTP, which also replaces the Webhook Secret. The secret can therefore change without any Partner call; signature failures after such a change are expected until the new secret is stored, and polling stays the fallback.
- Partner `sellers/api-key` (retrieve) does not return a callback secret; the only documented Partner route that returns one is regenerate (Observed; matches `geraiexpress-mengantar-partner-api.md` §6–7).
- Common signature failure causes include "using the wrong secret ... regenerating your API key also replaces the Webhook Secret" (Public).

Consequences under the DEC-006 one-seller-per-tenant model:

- [Proposal] Each tenant's seller has its own Webhook URL and its own secret. A shared platform webhook endpoint therefore holds one secret per seller, and because the body has no seller field (§4.2), the endpoint cannot choose the secret from the payload. Candidate mechanisms: a per-seller, unguessable URL path (the page calls a long unguessable path "a speed bump, not a substitute" and notes the path travels in every request), or trial verification against the stored secrets. Neither is documented by Mengantar; the second is also a timing/CPU cost. This is design input for the separate cookie-less webhook host of DEC-015, not a verified fact.
- [Proposal] Because only the seller can set the URL (signed-in Mengantar account) and a verification code is required, the tenant onboarding flow must include a manual seller-side step, and webhook readiness is a separate state from "connected". Until the secret is stored, the page's own recommended fallback is polling `GET …/order`, which stays the reconciliation path in any case.
- [Proposal] A lost `callbackSecret` after a rotation cannot be recovered from any documented Partner route (Observed: only regenerate returns it). The seller-side "regenerate Webhook Secret" setting is the documented recovery path.
- Unknown: whether the Partner can read the seller's Webhook URL or paused state; whether sandbox and production secrets differ per account (the page says use a different URL per environment, and every account has its own secret).

### 4.6 Sandbox testing

### 5.2 Get orders (`GET …/order`)

Query (Observed): `page` (default 1), `size` (default 50), `courier`, `cod` (`COD` or `NON_COD`), `status` (JSON object as a string, keys set to `true`), `dateRange` (`startDate`, `endDate`), `batch` (described as "Batch _id"), `tracking_id` and `order_id` (each returns a single order with a `history` array).

Observed behavior that contradicts the page (T-021, 2026-10-14): `dateRange` did not filter; `count`/`total` were always 0; `batch=` matched the batch **code** while the documented batch `_id` returned `[]`; list answers were newest-first by `createdAt`.

## 7. (f) Pay unpaid and batch endpoints

Anchors: `#content-pay-unpaid`, `#content-add-order`, `#content-get-batch`, `#content-delete-batch`. Access date 2026-10-28.

### 7.1 `POST …/order/pay-unpaid`

Request (Observed): `{courier, batch_id}`. `batch_id` is described as "**Batch _id (required)**" and the curl example uses a 24-hex object id (`6332f5b98c3ea4bc8e15f72d`). `courier` is optional for JNE (the default) and required for every other courier; Ninja can no longer be paid.

Response (Observed): `{success: true, data: <number of orders paid>, cnote_no: [<tracking numbers>]}` — `data` is a count, `cnote_no` an array at the top level of the envelope.

**`batch_id` is the batch `_id`, not the batch code.** Evidence in the documentation: the create-order response has both `batch` (e.g. `26013014BBQFMM`, the human code) and `batch_id` (e.g. `697c58034fa61abe7c700da6`, the object id) and the pay-unpaid field is named after, and described as, the `_id`. No observation of a live pay-unpaid call exists yet (T-020: orders were paid at creation).

Preconditions and failure modes (Observed): create-order creates an order with `isPaid: false` and `cnote_no: null` when the balance is insufficient, "the shipping fee has not been charged yet"; after top-up, "complete the payment using the Pay Unpaid Order API — the `cnote_no` will then be generated". Unknown: the error shape and HTTP status when the balance is still insufficient, whether payment of a batch is all-or-nothing, behavior when called twice for the same batch (idempotency), behavior on a mixed batch of paid and unpaid orders, and whether the returned `cnote_no` order matches the order of the batch's members. The existing client states the AWB order does not prove mapping (`src/lib/mengantar/public-api.ts:244`).

### 7.2 Batch reads

`GET …/batch` — §5.3. `orderData[]` lists members with `orderId`, `cnote_no`, `status`, `SPECIAL_INS`. Batch `_id` field in the response is `_id`; the human code is `id` in the same example (Observed), so one batch read yields both identifiers.

`DELETE …/batch` — §3.2.

### 7.3 Relation to the current code (Observed in this repository)

- The client sends `{ batch_id: batchId, courier }` (`src/lib/mengantar/public-api.ts:252`), validates the id with `BATCH_ID = /^[A-Z0-9]{6,24}$/` (`:391`, the uppercase code shape), and the dispatcher passes the stored batch code (`src/lib/mengantar/dispatcher.ts:270`). This is the defect recorded as P0-2 in `docs/review/2026-10-28-full-review.md`; this note adds the documentary basis. It is not fixed by this documentation task.
- The response parser reads `d.cnote_no` (array) but takes the count from `d.count ?? d.paidCount ?? d.paid_count ?? rawAwbs.length` (`:259-276`); with the documented shape `data` is a number so `d` is the envelope and `data` (the documented paid count) is not read — the count falls back to the AWB array length. Whether that matters depends on whether the two can differ, which is Unknown.
- Create-order sends one order per request (`:525-535`); the documentation recommends grouping into one batch for JT Premium and SiCepat (§1.7).

Arithmetic checks on the documentation's examples (Evidence, computed for this note):

- Seller and public estimate examples satisfy `estimatedSpecialPrice = price − discount + codFee` and `discount = discountPercent × price`.
- The Create Order response example does **not** satisfy it: item 1 shows `estimatedPrice 8000`, `discount 1600`, `estimatedSpecialPrice 5600`, where `8000 − 1600 = 6400`; the 5600 value corresponds to a 2400 reduction (30 percent of 8000). Item 2 (`estimatedPrice 11329`, `discount 1600`, `estimatedSpecialPrice 8929`) shows the same 800 gap to 2400. The page does not explain the difference; it is therefore **Unknown** whether `discount` excludes an extra discount that `estimatedSpecialPrice` includes, and whether this is the same thing as the `discountExtra*` fields. Do not rely on the docs example for the money rule. (Earlier T-019 observation: production `estimatedSpecialPrice` includes the COD fee, and administrator net cost was taken as `estimatedSpecialPrice − codFee`.)
- Create Order item 2 shows `COD_FEE` as the decimal `3329.99` while `estimatedPrice` is an integer; estimate `codFee` has been integer in all observations. The repository parser rejects a non-integer money value (`src/lib/mengantar/public-api.ts:345`, used at `:375`); an order-response `COD_FEE` is not parsed today. Rounding rules are Unknown.

### 8.4 Which variant is appropriate for a partner

- [Proposal] Use the seller estimate (`/order/estimate` with that tenant's own seller key) for quotes. It is the only variant documented to depend on the seller's own volume discount, it is the same figure family (`price`, `estimatedSpecialPrice`) that the created order echoes, and it is already implemented (`:181-194`). Per DEC-016 the customer pays `price` (+ COD fee); the discount fields feed only the private net-cost estimate.
- The public variant states a fixed 20 percent and Mengantar markup for all users, so it cannot show a seller's negotiated or volume discount; it would be a display-only reference rate. The 3PL variant is described as intended for "logistics partners and integrators" but its price basis is ambiguous (§8.1); use it only after Mengantar confirms how its `price` relates to the seller `price` and whether Partner access to it needs enablement.
- The owner's starting terms (provider 30 percent, gerai 20 percent) remain owner-stated and unverified (DEC-016). This documentation supports 20 percent only as a sandbox example and as the fixed public rate; the help-page volume steps (20, 22.5, 25, 27.5, 30 percent, with 30 only above the 10,000 step) are a separate vendor page and not part of the two documents read for this note.

### 8.5 Other limits stated on the estimate page (Observed)

SPX Express: maximum weight 50 kg, maximum COD Rp5,000,000, maximum non-COD goods value Rp10,000,000. Update 2026-11-02 (help 5387484 and 5502313, lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): regular-service maximum weight 50 kg (Lion 100 kg, Anteraja 30 kg); cargo minimums JTR 10–30 kg, Gokil 10–50 kg, IDX Kargo 10–70 kg, SAP Kargo 5–100 kg by region; per-courier COD maxima JNE, IDX, J&T, Lion and SPX Rp5,000,000, SiCepat Rp2,500,000, SAP Rp2,000,000, Anteraja Rp3,000,000, Pos COD Rp2,000,000 and non-COD Rp5,000,000; a weight difference found by the courier is debited from or credited to the seller's "saldo tersedia"; an iDexpress parcel under 0.5 kg pays up to half the fare. Pos Indonesia COD requires a delivered rate of at least 82 percent over a rolling 21–60 day window, with a three-day grace period; non-COD is unaffected; on create, a blocked COD answers 403 with `status` (`new_seller`, `insufficient`, `blocked`) and `deliveredRate`. Dangerous goods: supported regular couriers are SiCepat, SAP, iDexpress and J&T for estimate; create-order DG supports JT, SiCepat and iDexpress, and cannot be combined with cargo.

## 9. (h) Dropshipper endpoints — NOT used under DEC-017

Anchors: `#content-add-dropshipper`, `#content-search-dropshipper`, `#content-add-order`, `#content-orders`. Access date 2026-10-28.

Observed contract:

- `POST …/dropshippers` `{name, phone}` creates (or returns an exact-match existing) saved dropshipper; HTTP 201 `{success, data: {id, name, phone}}`. `GET …/dropshippers` searches by name/phone prefix (`search`, `page`, `perPage` ≤ 100). Both need the `createOrder` permission **and** the Dropshipper feature enabled for the account "through Seller Web"; otherwise 401 (key/permission) or 403 (feature disabled).
- Create Order may carry `orders[].dropShipper {id, name, phone}` per item referencing an existing saved dropshipper (never auto-created); the whole batch is validated first and rejected with 400 if any reference is invalid or name/phone mismatch.
- Implication for sender identity (Observed): "The canonical name and phone from the saved master become the shipment and label sender identity. The pickup address remains the seller address selected in the request." Orders without `dropShipper` "continue to use the seller identity". Get orders returns `dropShipperId` and `dropShipper` only for dropship orders.

Decision status: DEC-017 states the masked label is local, the operator-entered sender is never mapped to a provider dropshipper, and the Mengantar pickup name is never the default sender; DEC-013 keeps PR-3 customer-sender/dropshipper deferred. **GeraiExpress therefore does not call, store, or depend on these endpoints or on the `orders[].dropShipper` field.** The provider-side seller identity on a created order (pickup address `PICKUP_NAME`, `SHIPPER_NAME`) remains whatever the tenant's pickup address master holds; masking happens only on the locally printed label. A courier-side or provider-side printed label (not used) would show that provider identity. Whether provider-side sender identity ever reaches the recipient through courier SMS/WhatsApp is Unknown from the page.

Return destination (Observed 2026-11-02, help 14715369 updated 2026-10-17, lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): a seller return address is used only when origin and destination are both on Java, and only for JNE, SiCepat and SAP; otherwise "sistem akan menggunakan alamat pickup sebagai pengganti alamat retur". Create Order has no return-address field. Inference: an RTS parcel from an API order returns to the provider pickup address, never to a masked sender. Whether a return address saved in the seller's web settings applies to API orders is Unknown.

## 14. Claims (added 2026-11-02)

Observed (help 5207011, 5596208, 8140017 updated 2026-09-18, 6046101; lane D, `docs/research/evidence/2026-11-02/lane-d-mengantar-current.md`): there is no claims API; claims go through Live Chat (08:00–20:00 WIB).

- Claim types: return; full value (the COD amount or the insured value); other. A stuck-parcel claim pays "(Nilai COD/NON COD - estimated fee)".
- Processing: at most 14 days, paid to "Saldo Tersedia" (information, not a promise to a gerai).
- Filing windows, each with a unit and an anchor event:
  - JNE: 45 working days (Java, Sumatra, Bali, NTB) or 60 working days (other regions);
  - SiCepat, IDX, Anteraja, Pos: 14 days from the last status;
  - SPX: 14 days from RTS;
  - SAP: 60 days;
  - J&T, Lion: 30 days;
  - lost-claim within 3×24 h for IDX and J&T;
  - disputes after Delivered: 7–15 days.
- Exclusions: damage reported more than 3 days after receipt, a missing unboxing video, liquids over 100 ml, live plants.
- Lost status: see §5.1.
